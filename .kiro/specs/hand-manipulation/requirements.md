# Hand manipulation — Requirements

## Overview

Before this spec, hand tracking ran only during try-on: `useArmTracking` (`src/try-on/useArmTracking.ts`) started the MediaPipe worker (`src/try-on/arm.worker.ts`, one hand plus pose) when 護臂試戴 was on, and `ArmTracker` (`src/try-on/arm-pose.ts`) turned each frame into a cuff pose. Everything else in the workbench is driven by the mouse: click to pick a part, the transform gizmo (`TransformControls` in `src/scene/SceneViewport.tsx`) to drag it, OrbitControls to turn the view.

This spec lets the user work with both hands in the webcam view. It is capability C4 in `docs/VISION.md` (§2, §4.9 and its "Updated 2026-11-19 (both hands)" note). Its P0 core: hand tracking runs whenever the camera is on and follows up to two hands; both hand skeletons are drawn over the camera view; the camera image can be hidden while tracking continues; one hand pinches a part to move it, or pinches empty space to turn the view. Four P1 items follow, each its own task, cut from the end if time runs short: two-hand zoom, a fist that holds and moves a whole object (and, with the other hand, pulls it into the exploded view), two-hand rotate, and an agent tool that hides or shows the camera image.

The pinch stays the main action gesture, because a laptop webcam gives about one reliable "button" per hand. The second hand adds meaning without new poses: the first hand's target decides the gesture, and the second hand can only join that gesture, which then reads one number between the two hands (their distance or the angle of the line between them). The fist (P1) is the only new pose; it is detected from the landmarks with hysteresis, with no new model.

A hand move works on parts, like the mouse gizmo: it uses the gizmo's commit path, and precision comes from zooming in, as with the mouse. A fist move (P1) works on whole objects and uses the workspace's object transform, like the 物件 panel.

The tracking part is shared: `body-fit` (phase C) reuses it for try-on of any designed object, and later specs can read the raw landmarks.

**History.** Scope was decided with the user on 2026-11-15 for one hand and reviewed the same day ("Decisions from review"). On 2026-11-19 the user decided on two-hand control ("Decisions of 2026-11-19"). Tasks 1 and 2 were built and committed under the 2026-11-15 version and are kept; changes to their code are made in later tasks.

**Numbering.** Requirement numbers are stable ids, because the finished Tasks 1 and 2 refer to them. Requirements added on 2026-11-19 are numbered from 73 and placed in the section they belong to, so the numbers are not in order inside the document. Removed requirements keep their number with a "Removed" note.

## Goals

- Hand tracking runs whenever the camera is on, follows up to two hands with one worker shared by hand control and try-on, and a 手勢 switch turns hand control off.
- The user always sees, for each hand, whether it is seen and what it is doing, without relying on colour alone.
- The camera image can be hidden, so the user works with the hand skeletons over a plain backdrop, while tracking continues at the same rate.
- Pinch a part with one hand and drag it to move it, through the same commit path as the mouse gizmo; one gesture is one undo step. Pinch empty space with one hand to turn the view.
- With two hands (P1): zoom, hold and move a whole object with a fist and pull it apart, rotate a part. The first hand always decides the gesture, so gestures never collide, and one hand stays the default.
- Hand control switches itself off, or to view-only, with a notice, when grabbing would be unsafe or too slow, and never blocks the mouse.
- Every gesture decision is a pure function, unit-tested with synthetic landmark sequences; e2e tests drive the app with a scripted fake landmark source; no test needs a webcam.
- The thresholds that need tuning on a real webcam are named constants in one place, and `?hands=debug` shows the numbers needed to tune them.
- No regression: with the camera off the workbench behaves exactly as today, and try-on behaves as today.

## Out of scope

- Rotating whole objects by hand. The 物件 panel's number fields and the agent's `set_transform` do that. Moving whole objects by hand is the P1 fist (requirements 89–95).
- Moving or rotating parts in the exploded view. The displayed part positions include the explode offset, so grabbing parts is off there (requirement 41); a later item is listed under "How later specs fit".
- Two-hand gestures other than zoom, rotate and explode: two-hand snap assembly of two objects held by two fists (`assembly-joints`), a two-hand ruler, pulling a part out with one hand while the other holds the object, and an open palm to cancel. All are listed under "How later specs fit".
- A hand mode, mode buttons and mode keys. The rotate mode of the 2026-11-15 version is replaced by two-hand rotate, and double-pinch zoom by two-hand zoom (requirements 56–62, removed).
- Deciding hand roles by left or right. Roles go by which hand engaged first; MediaPipe's handedness labels are not used for hand control (requirement 78).
- Wrist-twist rotation. Palm-facing roll is ambiguous (`ROLL_FLIP_DOT` handling in `src/try-on/arm-pose.ts`).
- Resizing by hand, and any change to part dimensions by hand. Real size changes go through the agent or the number fields (§4.9 "Zoom and size are different things").
- Moving a part or an object towards or away from the camera by hand. A drag moves it in the plane facing the camera; the user turns the view to move along another axis.
- Dragging whole objects with the mouse.
- Snapping parts (C9), picking candidate thumbnails (C3) or floating project cards (C17) by hand.
- Agent or voice control of the 手勢 switch. The only new agent tool is the camera-image switch of requirement 99. The agent request keeps sending only `tryOn` and `cameraOn`.
- Any change to the try-on itself, the cuff, or `ArmTracker`'s placement logic. `body-fit` changes those.
- Any change to `ModelSpec`, `Part`, the workspace schema or the provider adapters. The server changes only for the tool of requirement 99 and its optional state-change flag.
- English UI.

## Functional requirements

### Shared hand tracking

1. Hand tracking runs while the camera is on and either the 手勢 switch is on (requirement 8) or try-on is active. It stops, terminating the worker, when the camera turns off or the page unloads. With the camera off, no tracking code runs and nothing is downloaded.
2. One tracking worker serves hand control and try-on. Turning try-on on or off while the camera and 手勢 are on does not restart the worker or reload a model.
3. Pose inference runs only while try-on is active. Outside try-on each frame runs only the hand landmarker. Whether the pose model is loaded at start or on first use is a design choice; either way the first try-on frame must not hit the worker's per-frame watchdog.
4. Raw landmarks are exposed for later specs through one small client API: the latest frame (image landmarks, metric world landmarks, handedness, body landmarks when pose ran, frame size, capture time) plus the tracker status and delegate. Consumers read it from a ref or subscribe to it; a new frame never causes a React re-render by itself.
5. Try-on consumes the same frames through `ArmTracker`, unchanged. The try-on status line (`data-testid="try-on-status"`), its texts and its stats (`try-on-stats`) behave as today, and `tests/e2e/arm-try-on.spec.ts` passes unchanged. Its fake worker is routed by URL, so the worker stays reachable at a URL that its route pattern matches (`src/try-on/arm.worker.ts` in dev, `assets/arm.worker-*.js` in a build), and its message protocol stays compatible: a frame without `world` landmarks or without `body` is still valid.
6. Tracking failures (load error, track error, load timeout) never affect the camera, the scene or the mouse. They only turn hand control off with a notice (requirement 43).
7. Frames are flipped before tracking exactly as today when the video is shown mirrored, so landmarks are in display space for both front and rear cameras.
73. **Two hands.** The worker tracks up to `TRACKED_HANDS` (2) hands per frame. Every tracked hand reaches every consumer: `ArmTracker` receives all hands of the frame, as it already does, so try-on keeps working and `arm-try-on.spec.ts` passes unchanged. Setting `TRACKED_HANDS` to 1 is a one-line change that restores the one-hand tracking cost; two-hand gestures then never start and everything else works.
74. **Cost of the second hand.** The speed gate of requirement 40 stays as it is (`MIN_CONTROL_FPS`, `SPEED_HOLD_MS`) and measures the rate with two hands allowed. The debug panel (requirement 45) shows the number of hands per frame and the inference time, so the cost of one and of two hands can be measured on the user's laptop. Design states the expected cost.

### 手勢 switch

8. A 手勢 toggle button in the camera toolbar turns hand control on and off. It has `aria-pressed`, is on by default, and is shown only while the camera is on. It is session state: turning the camera off resets it to on.
9. With 手勢 off: no hand-only inference runs while try-on is off (whether the worker is kept idle or terminated is a design choice); the hand overlay and the hand status line are hidden; no gesture acts; and the mouse works as today.
10. Try-on works with 手勢 off exactly as it does today; tracking then runs for try-on only, and the overlay stays hidden.
11. The button's accessible name, 手勢, does not match an existing test selector. New e2e tests select it, and every other new button, by exact name.

### Camera image (P0)

75. A 隱藏鏡頭畫面 toggle button (`type="button"`, `aria-pressed`) is shown in the camera toolbar, after 手勢, only while the camera is on. It stays enabled during agent runs. Its accessible name contains none of the texts that existing tests select without `exact` or that it could be confused with: 開啟攝影機, 關閉攝影機, 取消開啟, 即時攝影機背景 (the video's label), 手勢, 護臂試戴, 提高背景對比. (`arm-try-on.spec.ts` selects 關閉攝影機 and 即時攝影機背景 without `exact`.)
76. While it is pressed, the camera image is hidden:
    - The video element stays in the page with its stream and keeps playing. It is hidden with opacity or visibility, never with `display: none` and never by detaching the stream.
    - The viewport shows the same backdrop as with the camera off. The 3D scene, the hand skeletons, the try-on cuff and the status lines are unchanged.
    - Tracking continues at the same rate, whether or not the browser keeps calling `requestVideoFrameCallback` for a video it does not paint: the capture loop detects a stall and keeps capturing frames another way.
    - Mirroring and the landmark mapping are unchanged.
77. Whether the camera image is hidden is session state: not in the workspace, not an undo step, shown by default, and reset to shown whenever the camera turns off (stopped, failed to start, or the track ended). It does not depend on 手勢 or try-on. It is never sent to the server; the agent tool of requirement 99 can only set it.

### Hand overlay and badge

12. Whenever the camera and 手勢 are on and hands are tracked, the skeleton of each tracked hand (the 21 landmarks and the standard hand connections), up to two, is drawn over the camera view, including while hand control is off or view-only, during try-on and while the camera image is hidden. It lies on the user's hand in the displayed video: the mapping from normalised landmarks to screen positions accounts for the mirrored display and the `object-fit: cover` crop (`coverFrameBounds`). The mapping is one pure function shared with picking (requirement 22).
13. A hand's skeleton is hidden within `HAND_LOST_MS` of the last frame that contained that hand.
14. **Colour.** Both hands use the same skeleton colour. A second colour is used only for the line that joins the two hands during a two-hand gesture (requirement 86). The two colours are colour-blind-safe as a pair, and differ from the part-edge cyan (`HOLOGRAM.edgeColor` `#69eaff`) and the selection amber (`SELECTION.edgeColor` `#ffc53d`) in `src/scene/style.ts`. Colour never carries the state.
15. **State is shown by shape, not colour,** per hand: thin lines and no mark = tracked; a hollow ring at the cursor = over a part or an on-screen target; a filled ring and thicker lines = grabbing, turning the view, or taking part in a two-hand gesture as the second hand; grey dashed lines = hand control off or view-only and not turning the view, or a second hand that cannot join ("locked"). The locked style replaces the hand colour. With the fist (requirement 95) a rounded square at the palm replaces the ring.
16. A short Traditional Chinese badge is drawn next to each hand, so colour is never the only signal:

    | State | Badge |
    |---|---|
    | tracked | 手勢：待命 |
    | over a part | 手勢：對準 {part name} |
    | over an on-screen target | 手勢：對準 {target label} |
    | grabbing a part | 手勢：已抓取 {part name} |
    | turning the view | 手勢：轉動視角 |
    | locked | 手勢：暫停 |
    | a second hand that cannot join (requirement 81) | 手勢：另一手操作中 |

    The P1 requirements add their own rows (88, 95, 98). A name longer than 12 characters is cut to its first 12 characters followed by 「…」.
17. The overlay never receives pointer events, so mouse clicks, the gizmo and OrbitControls work through it. The badges are `aria-hidden`; the reasons hand control is off are announced through the hand status line (requirement 43).
18. The overlay element exposes its state for tests: `data-testid="hand-overlay"`; `data-hand-count` (0, 1 or 2); `data-hand-state` and `data-hand-target` for the hand in slot 0, and `data-hand2-state` and `data-hand2-target` for the hand in slot 1 (requirement 78); and `data-gesture`, the running gesture. Hand states are `none`, `tracked`, `hover`, `grab`, `orbit`, `locked`, `join` (the second hand of a two-hand gesture), and with the fist `fist` and `hold`. Gestures are `none`, `grab`, `orbit`, `press`, and with the P1 tasks `zoom`, `hold`, `explode` and `rotate`. A target is `{objectId}:{partId}` for a part, `screen:{id}` for an on-screen target, or empty. The `data-hand-mode` attribute of Task 2 is removed, because there is no hand mode.

### Cursor and pinch

19. Each hand's cursor comes from a stable point of the hand, `CURSOR_POINT` (default: the midpoint of the thumb tip and the index tip, landmarks 4 and 8, where the pinch closes), and is smoothed with its own One Euro filter (`CURSOR_MIN_CUTOFF`, `CURSOR_BETA`). The filter is a pure function of the point sequence and its timestamps and resets when that hand is lost.
20. The pinch distance is the distance between the thumb tip and the index tip in the metric world landmarks. A pinch **engages** when the distance stays below `PINCH_ENGAGE_M` (0.03 m) for `PINCH_ENGAGE_FRAMES` (2) consecutive tracking frames, and **releases** when it stays above `PINCH_RELEASE_M` (0.05 m) for `PINCH_RELEASE_FRAMES` (3) consecutive frames. Between the two thresholds the state does not change. A frame without world landmarks never engages a pinch; the skeleton is still drawn. **Changed on 2026-11-22 after the webcam test (requirements 103 and 104): the thresholds are 0.04 m and 0.055 m, and engaging and releasing are counted in milliseconds (`PINCH_ENGAGE_MS` 80, `PINCH_RELEASE_MS` 60) instead of frames.**
21. The pinch state machine is a pure function: (state, one tracking frame or a "no hand" frame, timestamp) → (next state, events). Its events are at least: hand found, hand lost, pinch engaged, pinch released, and tap (engaged and released without leaving the dead zone of requirement 29). Each hand has its own state.

### Two hands (P0)

78. **Hand slots.** Each hand found in a frame is assigned a slot, 0 or 1, which it keeps while it is tracked. Assignment uses screen positions, never MediaPipe's handedness labels: frames are mirrored before tracking, which inverts the labels, and the labels flip from frame to frame (36 times in the recording described in `docs/PRIOR_WORK.md`). A hand that appears takes the lowest free slot; with two hands and two tracked slots, the pairing with the smaller total movement wins; a hand that moved farther than `HAND_MATCH_PX` from a tracked slot is treated as a new hand. A slot whose hand is missing keeps its state until the time-outs of requirements 13 and 37. Two detections whose palm centres are closer than `DUPLICATE_HAND_PX` are one hand, and the second is dropped. Both rules are pure functions.
79. Each slot has its own cursor filter, pinch state, settled target, badge and mark, and with the fist its own fist state. One hand's frames never change the other hand's streaks, filter or settled target.
80. Requirements 22–39 describe one hand. They apply to the hand that starts a gesture (the owner, requirement 81). The other hand follows requirements 81–86.
81. **Arbitration.** At most one gesture runs at a time. The first hand whose pinch engages on a target that starts a one-hand gesture (`press`, `grab` or `orbit`, requirement 28), or, with the fist, whose fist engages on an object (requirement 91), becomes the gesture's **owner**. While the owner's gesture runs, the other hand cannot start a one-hand gesture: its pinch or fist either **joins** as the second hand of a two-hand gesture (requirement 82) or is **inert** until it is released. An inert hand is shown locked with the badge 手勢：另一手操作中 and changes nothing. A pinch whose decision is `none` (requirements 27, 42) owns nothing, so the other hand stays free. If both hands engage in the same tracking frame, the hand in slot 0 is handled first.
82. **The first hand decides.** The owner's gesture decides which two-hand gesture a joining hand starts. The joining hand's own target is not used in this spec (later specs may use it):

    | Owner's gesture | Joining hand | Two-hand gesture | Reads | Requirement |
    |---|---|---|---|---|
    | turning the view (a pinch on empty space, or on any part while view-only) | pinch | zoom | distance | 87 (P1) |
    | grabbing a part | pinch | rotate | angle | 96 (P1) |
    | holding an object with a fist | pinch | explode | distance | 93 (P1) |
    | anything else | pinch or fist | none: the hand is inert | — | — |

    The rule is one pure function of the owner's gesture, the joining hand's input (pinch or fist) and target, and the hand-control gates. Each P1 task adds its own row; a row whose task is cut is absent, so the joining hand is inert. In the P0 tasks every row is absent.
83. **Pair geometry.** Pure helpers give the distance (CSS pixels) and the angle (degrees) of the vector from the owner's gesture point to the joining hand's cursor. The owner's gesture point is its cursor for a pinch and its palm centre for a fist. Each two-hand gesture reads only one of the two numbers, relative to its value when the joining hand engaged, after a dead zone. Leaving the dead zone does not jump: the dead zone is subtracted from the change. The angle is read only while the distance is at least `TWO_HAND_MIN_SPAN_PX`, and angle changes wrap to ±180°.
84. **Hand-off between one and two hands.** During a two-hand gesture, the owner's one-hand effect (moving the part or object, turning the view) holds still. When the joining hand releases, or has been missing for longer than `TRACKING_LOSS_MS`, the two-hand gesture ends and keeps its effect so far (zoom: the view; explode: the amount; rotate: the previewed rotation, which is still committed or cancelled with the owner's gesture). The owner then continues its one-hand gesture from where it is, re-based to its current position so nothing jumps. When the owner's gesture ends (release, tracking loss, cancel), the two-hand gesture ends with it, and the joining hand's pinch or fist is inert until it is released; it never takes over the owner's gesture.
85. **One hand stays the default.** Two-hand gestures are short adjustments, because holding both arms up tires the user quickly. No result needs both hands held up to stay, and each two-hand gesture has a one-hand or mouse equivalent: zoom has the mouse wheel and the zoom buttons; rotate has the gizmo's 拖曳旋轉 and the 角度 fields; explode has the 爆炸圖 button and slider. The hint of requirement 43 names only one-hand gestures.
86. **Two-hand feedback.** While a two-hand gesture runs, a line in the second colour (requirement 14) joins the two gesture points; the joining hand shows the `join` state (filled ring, thicker lines) and a badge that names the gesture and its value (requirements 88, 95, 98); and `data-gesture` names the gesture.

### Picking and targets

22. Hand picking has two kinds of targets. **On-screen targets** are checked first, in screen space, against their on-screen rectangles; this spec registers none, and later specs add them. If none is under the cursor, a ray is cast from the cursor's canvas position into the scene, against the same part surfaces of all objects that a mouse click uses, and the nearest hit is taken. Hand picking does not cycle through parts behind each other the way repeated clicks do. On-screen targets are a list that later specs can add to (candidate thumbnails, floating project cards) without changing the picking, pinch or settling code.
23. Each hand's **settled target** changes only after a new raw target (an on-screen target, a part, or empty space) has held for `HOVER_SETTLE_MS` (150 ms). The badge, the ring and the target attributes show the settled target, and a pinch acts on the settled target at the moment it engages, so the small cursor movement while the fingers close does not change what is grabbed. The settling rule is a pure function.
24. A pinch whose settled target is a part of the **active object** selects that part alone, as a plain click does, and grabs that part.
25. A pinch whose settled target is a part of an **inactive object** makes that object active, selects that part alone, and grabs that part, all in the same gesture. Making the object active follows the workspace rules (clears the selection, resets explode, turns off the gizmo) and is not an undo step.
26. A pinch whose settled target is empty space turns the view (requirement 35). It never changes the active object or the selection.
27. A pinch whose settled target is an on-screen target presses it if the pinch is a tap (requirement 29); a drag that starts on an on-screen target does nothing. Pressing works when hand control is fully on or view-only, not when it is off. Apart from that, with no objects on stage, a pinch does nothing.
28. The decision "what does this pinch do" is one pure function of the settled target, the active object id and the hand-control gates (requirements 40–42), returning `press(targetId)`, `grab(objectId, partId)`, `orbit`, or `none`. It is applied to a hand that may start a gesture; a second hand goes through requirements 81–82.

### Pinch-move (P0)

29. A grab becomes a drag when the filtered cursor leaves a dead zone of `DRAG_DEAD_ZONE_PX` around its position at engage. A grab released inside the dead zone is a tap: it only selects (requirements 24–25) and creates no undo step.
30. During a drag the grabbed part moves in the plane that passes through the grabbed point and faces the camera. The movement is relative to the pinch start: the cursor's offset since engage, times `DRAG_GAIN`, is converted to a world offset at the grabbed point's depth, then into the part's parent frame (its parent part, or the object root for a root part, including the object's transform), and added to the part's position at engage. The part therefore never jumps when the pinch engages. The mapping is a pure function of the camera, the parent frame's world matrix, the start position, the grabbed point and the cursor offset.
31. **Precision comes from zooming in, as with the mouse.** Because the offset is converted at the grabbed point's depth, one screen pixel is a smaller move when the camera is closer. Zooming in (mouse wheel, the zoom buttons, or the P1 two-hand zoom of requirement 87) gives finer moves. There is no separate precision mode.
32. A drag is a preview: only the part's scene node moves while the hand drags, as during a gizmo drag, and its child parts follow it exactly as they do with the gizmo. The workspace is not changed during the drag. On release the final position is committed once through the same path as the gizmo (`onTransform` → the part update of the active object), as one undo step, with the notice 已移動零件，可按「復原」回到上一步。 Child parts' stored positions stay relative to their parent and are unchanged. A drag that ends where it started commits nothing.
33. The committed position is rounded to 5 decimals, as the gizmo rounds it, and kept within ±100 m per axis (the `Part` position limit), so the commit always passes validation. The part's rotation and the object's transform are unchanged by a move.
34. During a drag the mouse gizmo cannot be dragged, and a mouse drag that is already running blocks a new pinch; the two never move the scene at the same time.

### Turning the view (P0)

35. A pinch on empty space turns the camera around the orbit target while the pinch is held: horizontal cursor movement changes the azimuth and vertical movement the polar angle, relative to the pinch start, with gain `ORBIT_DEG_PER_PX`, within OrbitControls' existing limits. It changes no data, creates no undo step, and shows no notice.
36. Turning the view by hand counts as a user view change: a later resize keeps the view instead of reframing, as after a mouse orbit, and 重設視角 frames all objects as today.

### Tracking loss and cancel

37. If the owner hand is lost during a drag, the preview holds still. If the hand returns within `TRACKING_LOSS_MS` (300 ms), the drag continues. Otherwise the policy constant `ON_TRACKING_LOSS` decides: `'cancel'` (default) puts the part back where it was at engage, commits nothing and shows 手部追蹤中斷，已取消這次移動。; `'keep'` commits the last preview position through the part update path as one undo step. Changing the default is a one-line change to that constant. A lost joining hand follows requirement 84.
38. A hand lost while turning the view simply stops the turn; the view stays where it is.
39. A drag is also cancelled and the part put back, with no commit and no undo step, when, before release: grabbing turns off (hand control fully off or view-only, requirements 40–41), 手勢 is switched off, the camera turns off, the page is hidden, or the workspace changes from any other source (undo, redo, the 物件 panel, a part field, an agent `state` event, the active object changing, or the grabbed part or its object being removed or replaced).

### When hand control is off

40. Hand control is fully off (no grab, no view turning) while: try-on is active; or the measured hand-tracking rate stays below `MIN_CONTROL_FPS` (~~10~~ **5** frames per second, changed on 2026-11-22, requirement 105) for `SPEED_HOLD_MS` (2 s). It counts as fast enough again after the rate stays at or above the floor for `SPEED_HOLD_MS`. The delegate does not matter: one or two hands without pose may be fast enough on the CPU, and a GPU start-up failure that falls back to the CPU must not remove gestures while the rate is fine. The delegate is still shown in the debug panel (requirement 45). The skeletons are still drawn, in the locked style.
41. While an agent run is active, or while the exploded view is open (explode above 0, or still animating back to assembled), hand control is **view-only**: a pinch on empty space or on any part turns the view, two-hand zoom works (requirement 87), and grabbing parts is off. In the exploded view the displayed part positions include the explode offset, so committing a hand drag would write that display offset into the model; the gizmo is disabled there for the same reason. With the fist, holding and moving a whole object stays possible in the exploded view but not during an agent run (requirement 94). The skeleton shows the hand colour while turning the view and the locked style otherwise.
42. Hand control returns to full control by itself when the reason ends. A pinch that is still held at that moment does nothing until it is released.
43. A hand status line (`role="status"`, `data-testid="hand-status"`, `data-state`) below the camera view shows at most one Traditional Chinese line while the camera and 手勢 are on, in this priority:

    | Situation | Text |
    |---|---|
    | tracker loading | 正在載入手部追蹤模型（第一次約 20–30 秒）。 |
    | load or track error | 手部追蹤無法使用，仍可用滑鼠操作。 |
    | tracking too slow (requirement 40) | 這台電腦的手部追蹤太慢，手勢已停用；骨架仍會顯示，請用滑鼠操作。 |
    | try-on active | (nothing: the try-on status line already shows) |
    | agent run active | 代理執行中，手勢只能轉動視角。 |
    | exploded view open | 爆炸圖開啟中，手勢只能轉動視角；收回後即可抓取零件。 (requirement 94 changes this line) |
    | gesture cancelled by tracking loss (for about 4 s) | 手部追蹤中斷，已取消這次移動。 |
    | no hand seen yet | 把手舉到鏡頭前：捏住零件可移動，捏住空白處可轉動視角。 |

    With the camera off or 手勢 off the line is not rendered. Design may refine the wording; the states stay.
44. The 手勢 switch, the hidden camera image (requirement 77), the hand slots and the hand states are session state, outside the workspace (workspace-v2 requirement 11), and are never undo steps.

### Debug statistics

45. With `?hands=debug` in the page URL, a small panel shows: delegate, tracking frames per second, mean inference time, the number of hands in the latest frame; per hand, the current pinch distance in mm, the pinch state and the settled target (with the fist also the curl ratio and the fist state); the running gesture; and counters for drags, commits, cancels, tracking losses during drags, the longest gap during a drag in ms, two-hand gestures started and inert second-hand pinches. Without the parameter the panel is not rendered and the counters cost nothing visible.
46. The counters stay in the browser. They are never sent to the server or a model, and never logged to the console per frame.

### Two-hand zoom (P1)

87. While the owner hand turns the view (requirement 35) and the other hand pinches anywhere, the turn holds still and the change in distance between the two cursors zooms the view: the camera's distance to the orbit target becomes its distance when the second hand joined, times (the distance between the cursors at join ÷ the current distance). The change in cursor distance is reduced by `ZOOM_DEAD_ZONE_PX`, and neither distance is taken below `TWO_HAND_MIN_SPAN_PX`. Spreading the hands zooms in; bringing them together zooms out; the angle between the hands is ignored. The camera distance stays within OrbitControls' minimum and maximum distance. Two-hand zoom is display only: no data change, no undo step, no notice. It counts as a user view change (requirement 36), and it works when hand control is fully on or view-only, not when it is off.
88. The joining hand's badge is 手勢：雙手縮放 and `data-gesture` is `zoom`. When the second hand lets go, the first hand continues turning the view from where it is, without a jump (requirement 84). E2E covers: one hand pinches empty space, the second hand pinches and moves away from the first, and the camera ends closer to the orbit target (`data-camera-position`, `data-camera-target`) with `data-model-json`, `data-object-json` and 復原 unchanged; moving the hands together zooms out; after the second hand lets go, moving the first hand turns the view with no jump; the same works with the exploded view open.

### Fist: hold, move and explode (P1)

89. **Fist detection.** A fist is a pure function of the metric world landmarks, with no new model. The curl ratio is the largest, over the index, middle, ring and little finger, of (distance from the fingertip to the wrist) ÷ (distance from that finger's knuckle to the wrist). A fist **engages** when the curl ratio stays below `FIST_ENGAGE_RATIO` for `FIST_ENGAGE_FRAMES` consecutive tracking frames and **releases** when it stays above `FIST_RELEASE_RATIO` for `FIST_RELEASE_FRAMES` frames (**changed on 2026-11-22, requirement 104: `FIST_ENGAGE_MS` 150 and `FIST_RELEASE_MS` 60 replace the two frame counts**); between the two nothing changes, and a frame without world landmarks never engages a fist. A hand lost while its fist is engaged follows the same time-outs as a pinch (requirement 37). `FIST_ENABLED = false` turns fists off completely: no fist state is computed, and the pinch works exactly as without requirements 89–95.
90. **Fist and pinch.** A frame whose curl ratio is below `FIST_ENGAGE_RATIO` never counts toward engaging a pinch. A hand whose engaged pinch has left the dead zone never engages a fist. If a fist engages while the same hand's pinch is engaged but has not left the dead zone, that pinch's gesture is cancelled with nothing committed, and the fist takes over: closing the hand passes through a short thumb–index distance on the way. **Changed on 2026-11-26 (requirement 117):** this holds for a hand that is not part of a two-hand gesture; a pinch that takes part in one is never replaced by a fist.
91. **What a fist holds.** When a fist engages, it holds the object whose part surface is nearest under the palm centre at that moment. There is no settling, because the palm centre stays still while the fingers curl. A fist on a part of an inactive object makes that object active (workspace rules, not an undo step). A fist over empty space holds nothing until it opens. A fist that holds an object becomes the gesture's owner (requirement 81); a fist made while another gesture runs is inert (`assembly-joints` adds a row for a second fist, see "How later specs fit").
92. **Moving a whole object.** Moving the fist moves the held object like a part drag (requirements 29–30), with the palm centre as the point, the world as the parent frame, the same dead zone and `DRAG_GAIN`, and the grabbed point's depth. The move is a preview of the object's scene node; its parts follow and the workspace does not change. On release it is committed once through the workspace `setTransform` operation, the same path as the 物件 panel, as one undo step with the 物件 panel's notice 已調整物件位置，可按「復原」回到上一步。 The object's rotation is unchanged; the position is rounded to 5 decimals and kept within ±100 m per axis; a hold released inside the dead zone commits nothing. Tracking loss and cancel follow requirements 37 and 39, putting the object back.
93. **Pulling it apart.** While a fist holds an object, the other hand's pinch, anywhere, joins (requirement 82): the change in distance between the fist's palm centre and the pinch cursor sets that object's explode amount, as the amount when the pinch joined plus (the change, reduced by `EXPLODE_DEAD_ZONE_PX`) ÷ (`EXPLODE_FULL_FRACTION` × the viewport height), kept within 0–1. The angle is ignored. The explode amount is the same display state the 爆炸圖 button and slider set: no data change and no undo step, and the button and slider follow it. The object's move holds still during the pull and continues, re-based, after it (requirement 84).
94. **Gates for the fist.** Holding, moving and pulling apart work when hand control is fully on and while the exploded view is open (moving the whole object does not touch the part offsets, so it is safe there). They are off during an agent run, during try-on and while tracking is too slow. Grabbing parts with a pinch stays off in the exploded view (requirement 41). With the fist, the 爆炸圖 status line becomes 爆炸圖開啟中，捏合只能轉動視角，握拳仍可移動整個物件；收回後即可抓取零件。
95. **Fist feedback and tests.** A fist shows a rounded square at the palm centre instead of the ring: hollow for a closed fist that holds nothing (state `fist`, badge 手勢：握拳), filled with thicker lines while it holds an object (state `hold`, badge 手勢：握住 {object name}). The joining hand's badge during a pull is 手勢：拉開 {n}% with the current explode percentage, and `data-gesture` is `hold` or `explode`. The square differs from the pinch ring by shape, so colour is not needed. E2E covers: a synthetic fist on the demo object moves the whole object (`data-object-json` changes, `data-model-json` does not) and one 復原 restores it; a fist on an inactive object makes it active; a fist plus a pinch moving away raises `data-explode` without an undo step; a fist in the exploded view still moves the object; a pinch-to-fist close on a part does not move the part. `FIST_ENABLED = false` is covered by unit tests.

### Two-hand rotate (P1)

96. While the owner hand grabs a part (requirements 24–30) and the other hand pinches anywhere, the part's move holds still and the change in the angle of the vector between the two cursors rotates the part about the camera's view axis through the part's origin, so that the part turns on screen the same way the vector turns. The distance between the hands is ignored; `ROTATE_DEAD_ZONE_DEG` is subtracted from the change; the angle is read only while the hands are at least `TWO_HAND_MIN_SPAN_PX` apart. The result is expressed as the part's rotation in its parent frame, in XYZ Euler degrees rounded to 2 decimals and within ±360°. The part's position is not changed by the rotation, and its child parts follow it.
97. The rotation is a preview. It is committed once, together with any move, when the owner hand releases, through the gizmo's `onTransform` path, as one undo step, with a notice that says what changed: 已移動零件，可按「復原」回到上一步。, 已旋轉零件，可按「復原」回到上一步。 or 已移動並旋轉零件，可按「復原」回到上一步。 Tracking loss and cancel (requirements 37, 39) put back both the position and the rotation. When the second hand lets go first, the previewed rotation stays and the first hand continues moving the part (requirement 84). Gates are those of moving: full control only.
98. The joining hand's badge is 手勢：雙手旋轉 {n}° (the signed angle so far), the line between the hands is drawn with an arc at the owner's cursor that shows the angle, and `data-gesture` is `rotate`. There is no rotate mode: no mode buttons and no G or R mode keys, and R stays 重設視角. E2E covers: grab a part with one hand, pinch with the other and move it around the first, release the second hand and then the first: only that part's rotation changes in `data-model-json` (its position is unchanged) and one 復原 restores it; a turn smaller than the dead zone changes nothing.

## How later specs fit (not built here)

- **assembly-joints** (new spec, C9): two-hand snap assembly of two objects, each held by a fist. It adds one row to the join rule (owner holds an object with a fist, joining hand makes a fist on another object → `assemble`), which is why the join rule receives the joining hand's input and target (requirement 82). The scene's object hold sessions are per hand and do not refuse a second one while the first runs, so the second fist can hold the second object. The two holds preview both objects, the joint spec detects the snap and shows the "joined" cue, and the commit becomes one workspace change for both objects and the joint.

## Decisions from review

The decisions were reviewed on 2026-11-15, in two rounds. The requirements above reflect the outcome, except where a decision of 2026-11-19 replaced it.

1. **Rejected: a pinch moves the whole object.** A pinch on a part moves that part (requirements 24–25, 29–34, 37, 39). The user prefers part-level moves, as in Blender, through the same commit path as the mouse gizmo (`onTransform` → the part update; the position is in the parent part's frame and child parts follow). Precision comes from zooming in, as with the mouse (requirement 31). A pinch on a part of an inactive object makes the object active, selects that part and grabs it in the same gesture; activation is not an undo step. Whole-object moves came back on 2026-11-19 as a separate pose, the fist (requirements 89–95), so the pinch still moves parts.
2. **Superseded on 2026-11-19: a separate hand mode, switched by hand.** The 2026-11-15 version had a 移動 / 旋轉 hand mode with on-screen mode buttons, G/R keys, and 重設視角 moved to Home. Two-hand rotate replaces it, so no mode, mode button or mode key is added and R stays 重設視角. What remains from this decision is the two-kind picking (on-screen targets first, then parts), kept so later specs can add targets (requirement 22).
3. **Accepted: view-only in the exploded view and during an agent run.** Turning the view changes no data, so it stays allowed there; grabbing parts is off (requirement 41). In the exploded view grabbing would also commit the explode offset into the model. Since 2026-11-19, two-hand zoom is allowed in view-only states, and a fist may move a whole object in the exploded view (requirement 94).
4. **Accepted with a change: "too slow" is measured only.** Hand control is fully off when the rate stays below `MIN_CONTROL_FPS` (10) for `SPEED_HOLD_MS` (2 s), whatever the delegate (requirement 40). Below about 10 fps the 2- and 3-frame pinch hysteresis alone takes 200–300 ms, and a drag visibly stutters. The CPU delegate alone does not turn hand control off: one hand without pose may be fast enough on the CPU, and a GPU start-up failure that falls back to the CPU should not remove gestures while the rate is fine.

Also changed in review: the status line says 代理 instead of AI 助理 (requirement 43); the badge keeps the part name, shortened after 12 characters (requirement 16); a 手勢 switch was added (requirements 8–11).

## Decisions of 2026-11-19 (both hands)

Decided with the user on 2026-11-19, because one hand was too limiting (VISION §4.9, "Updated 2026-11-19 (both hands)").

1. **Both hands are tracked and drawn (P0).** The worker allows two hands, both skeletons are drawn, and cursor, pinch and target state are per hand (requirements 12, 73, 78–79). The second hand costs tracking time; the speed gate stays, and `TRACKED_HANDS = 1` is the fallback (requirements 73–74).
2. **The first hand owns the gesture; the second can only join.** This follows Guiard's kinematic chain model of bimanual action (Y. Guiard, "Asymmetric division of labor in human skilled bimanual action: The kinematic chain as a model", *Journal of Motor Behavior* 19(4), 1987): the non-dominant hand sets the frame of reference and the dominant hand acts within it. Here the first hand sets the frame (it holds the part, the object or the view) and the second hand acts on it (zoom, rotate, explode). Roles go by order, not by left or right, because the handedness labels are unreliable on mirrored frames (requirements 78, 81–82).
3. **Each two-hand gesture reads one number.** Zoom and explode read only the distance between the hands, rotate only the angle, each with a dead zone, so a gesture never changes two things at once by accident (requirement 83). Apple's visionOS guidelines use the same two-hand patterns (pinch with both hands and drag apart or together to zoom; drag in a circle to rotate) and advise offering an alternative to gestures that need both hands (Apple Human Interface Guidelines, "Gestures"), which requirement 85 does.
4. **Hand-off between one and two hands.** Meta's Interaction SDK `Grabbable` uses a one-grab transformer while one hand holds and a two-grab transformer while two do. The same hand-off applies here: when the second hand lets go, the first hand's gesture continues from where it is, re-based so nothing jumps; when the first hand lets go, everything ends (requirement 84).
5. **The fist is the only new pose (P1).** It is a pure rule on the world landmarks with hysteresis, no new model, and `FIST_ENABLED` turns it off if it proves unreliable on the user's webcam (requirement 89). A fist holds whole objects and commits through the workspace's object transform; it works in the exploded view, where part grabbing stays off (requirements 91–94).
6. **The camera image can be hidden (P0), and the agent can hide it (P1).** Tracking keeps running while the image is hidden (requirements 75–77, 99–100).
7. **Two-hand zoom replaces double-pinch zoom, and two-hand rotate replaces rotate mode.** Requirements 56–62 are removed; R stays 重設視角.
8. **Cut order:** the agent switch first, then two-hand rotate, then the fist, then two-hand zoom (requirement 71). This matches the order of VISION §5, which cuts rotate, then fist, then zoom, with the agent switch added in front.

## Changes after the webcam test (2026-11-22)

Decided with the user after the first test on the user's laptop (VISION §4.9, "Updated 2026-11-22"). Findings: one hand tracks at about 9–10 fps (70–90 ms recognition); a closed pinch measures about 26 mm, half open about 58 mm, open about 100 mm, so the 30 mm engage threshold missed pinches; a release took 3 frames (about 0.3 s) while the opening hand kept dragging the object, so pinch-move, the view turn and the two-fist join (`assembly-joints` Task 6) overshot or failed on release; with `?hands-min-fps=5` everything else felt smooth. Built in Task 10. These requirements change numbers or rules of requirements 20, 40, 45, 47 and 89 (each is marked where it is stated above) and add the freeze; every other requirement stays as written. The join with two pinches and the fist-knob rotate of the same decision are a later task (Task 11) and are not part of this section. Task 12 (requirement 117, last in this section) changes the one-hand rule of requirement 90 for hands in a two-hand gesture.

101. **Freeze while a hand opens.** A hand is *opening* while its pinch is engaged and its distance rises above `PINCH_ENGAGE_M`, or while its fist is engaged and its curl ratio rises above `FIST_ENGAGE_RATIO`. While the owner or the joiner of the running gesture is opening, no hand movement is applied to the running session: the grab, the view turn, the zoom, the rotate, the hold, the explode and the assemble all keep their last preview, and the preview stays where it was. An opening hand cannot turn a tap into a drag. When the release is confirmed (requirement 104), the frozen state is committed by the rules the gesture already has (one undo step, notices, cancel rules). A tracking loss while frozen follows requirements 37 and 39. If every hand of the gesture closes again before the release is confirmed (the distance is no longer above `PINCH_ENGAGE_M`, the curl ratio no longer above `FIST_ENGAGE_RATIO`), the gesture resumes from the frozen point with a re-base, so nothing jumps; a two-hand gesture measures again from the current hands.
102. **Latched snap.** In the two-fist assemble session (`assembly-joints`), a snap that is ready when either hand starts to open stays ready through the freeze: the scene is not asked while a hand opens, the label 可以接合 stays, and the confirmed release commits that join. It is released only by the existing release rules, and only while the hands are not opening: when both hands have closed again the scene is asked as before.
103. **Pinch thresholds (changes requirement 20).** `PINCH_ENGAGE_M` is **0.04 m** (was 0.03 m) and `PINCH_RELEASE_M` is **0.055 m** (was 0.05 m). The measured closed pinch (about 26 mm) engages, the half-open hand (about 58 mm) does not.
104. **Time instead of frames (changes requirements 20 and 89).** `PINCH_ENGAGE_FRAMES`, `PINCH_RELEASE_FRAMES`, `FIST_ENGAGE_FRAMES` and `FIST_RELEASE_FRAMES` are removed. A pinch or a fist engages or releases when its distance (curl ratio) has stayed beyond the threshold for `PINCH_ENGAGE_MS` (80), `PINCH_RELEASE_MS` (60), `FIST_ENGAGE_MS` (150) or `FIST_RELEASE_MS` (60), measured from the first qualifying tracking frame, **and** for at least `MIN_GESTURE_FRAMES` (2) consecutive qualifying tracking frames, so one noisy frame never triggers. A frame that does not qualify, a frame without a distance or curl ratio and a frame without a hand restart the count; a video frame without a tracking result does not count. At 10 fps a pinch engages in 2 frames and releases in 2 frames; at 30 fps the time is about the same (4 frames to engage, 3 to release). `HAND_LOST_MS`, `TRACKING_LOSS_MS` and `?hands-loss-ms` are unchanged.
105. **Speed gate (changes requirements 40 and 74).** `MIN_CONTROL_FPS` is **5** (was 10), because the user's laptop tracks at about 9–10 fps. `?hands-min-fps` still overrides it. The README statement of the threshold and every test that assumed 10 follow.
106. **Debug line (extends requirement 45).** With `?hands=debug` the line shows the pinch engage and release thresholds in mm (捏合門檻 40／55 mm), so the next webcam test can read them next to the measured pinch distance. The manual webcam list of `tasks.md` gets an item for this task: pinch, drag and release several times and note any overshoot on release; repeat the two-fist join and note whether it joins on release; note any missed or false pinches with the new thresholds.
107. **Tests.** Unit tests cover the new thresholds, the time-based engage and release at 10 fps and at 30 fps spacing, a single noisy frame (no engage, no release), the freeze (the object does not move while the hand opens), the resume without a jump, and the latched snap committing on release. An e2e case covers a release while moving: the committed position is where the hand started to open. Existing hand tests change only where they encode the old numbers or frame counts; `tasks.md` Task 10 lists which.

### Join with two pinches and the fist knob (Task 11)

The two remaining decisions of the same webcam test (VISION §4.9, "Updated 2026-11-22"), which the first paragraph of this section left for a later task. They add two rows to the join rule of requirement 82 and change nothing else in it.

108. **Join with two pinches.** While the owner hand grabs a part of object A (a pinch grab, requirements 24–25) and the other hand pinches a part of a **different** object B that is not in A's assembly, the join rule gives `assemble`, at gate `full` only (as for two fists, `assembly-joints` requirement 59). The joining hand's settled target at engage picks the row. A pinch on a part of the same object, on a part of an object in A's assembly, on empty space or on an on-screen target is not an assemble: it keeps the rotate by circling of requirement 96. With `FIST_ENABLED = false` the row stays, because it reads pinches only.
109. **The switch from a part grab to two holds.** When the rule gives `assemble`, the owner's part grab is cancelled first: the part goes back to its stored position, nothing is committed, there is no undo step, and no cancel notice or cancel count (this is a change of gesture, not a loss). Then both hands hold whole objects, as in `assembly-joints` requirements 60–62: the owner's cursor holds A's assembly and the joiner's cursor holds B's assembly, each with the hold mapping of requirement 92 and the cursor as the point, measured from where each hand is at the switch, so that nothing jumps. A pinch that has not left its dead zone offsets nothing, as for a fist. If the scene refuses the holds, the grab is gone and both hands are inert until they open (the second pinch is counted as inert).
110. **After the switch** the gesture is the two-fist assemble with pinches: facing faces snap, the 可以接合 cue shows, the snap stays latched while a hand opens (requirement 102), and the owner does not freeze. Either pinch releasing (requirement 104) ends the gesture for both hands and commits through `onAssemble` exactly as for fists: with a ready snap, the moves and the new joint as one undo step and the joint card opens; without one, the moves of both objects as one undo step, or nothing when neither moved. The pinch that is still closed is inert until it opens. Losing either hand for longer than `TRACKING_LOSS_MS` and every cancel reason of requirement 39 follow `ON_TRACKING_LOSS` for both objects, and a joint is never created on loss or cancel. A gate change away from `full` cancels. Requirement 101 applies: a pinch that opens freezes both holds.
111. **Feedback of the pinch join.** Both hands show the state `hold` with a filled ring at the cursor (not the square of a fist), `data-gesture` is `assemble`, the badge is 手勢：捏住 {object name} for each hand until the snap is ready, and 手勢：可以接合 on the joining hand while it is ready (`assembly-joints` requirement 63). The fist assemble keeps 手勢：握住 {object name} and the square.
112. **Fist-knob rotate.** While the owner hand grabs a part and the other hand makes a fist (requirement 89), anywhere, the join rule gives `rotate`, at gate `full` only. The part turns about the camera's view axis through its origin by the twist of the fist: the change, since the fist engaged, of the on-screen angle of the vector from the wrist (landmark 0) to the middle-finger knuckle (landmark 9), accumulated frame by frame with angle changes wrapped to ±180° (so a full turn does not wrap back to 0), with `ROTATE_DEAD_ZONE_DEG` subtracted from the total as in requirement 96. The landmarks are in display space (requirement 7: the frame is flipped before tracking when the camera image is mirrored), so the angle is the one the user sees: turning the fist clockwise on screen turns the part clockwise on screen, with a mirrored or a plain camera view. The fist's position, its distance to the owner and the angle between the hands do not matter and move nothing; the angle is read whatever the distance between the hands is. A wrist–knuckle vector of zero length is not read.
113. **What the knob shares with the circling rotate** (requirements 96–98): the same preview (`rotateAboutView` through the grab session's `rotate`), the same commit kinds (`rotate`, or `both` when the owner also moved the part), the same notices, the owner's move holding still while the fist turns, the fist's release or loss keeping the shown rotation and re-basing the owner (requirement 84), the owner's release committing once, the badge 手勢：雙手旋轉 {n}° on the joining hand, the line between the hands, the arc at the owner's cursor, and `data-gesture` `rotate`. The joining fist shows the state `join` with a filled rounded square at the palm centre instead of a ring.
114. **Order decides.** A fist first and then a pinch stays the explode of requirement 93; a pinch grab first and then a fist is the knob. A fist that was already closed over empty space when the grab began holds nothing and joins nothing: it must open and close again. A fist that closes over an object while nothing runs holds that object, as before. Requirement 101 applies to the knob fist: its curl ratio rising above `FIST_ENGAGE_RATIO` freezes the turn, closing it again resumes from the current angle with a re-base, and the confirmed release keeps what was shown.
115. **Join rule after Task 11.** Requirement 82's table gains: owner grabbing a part + joining pinch on a part of another object outside the owner's assembly → assemble (108); owner grabbing a part + joining fist → rotate (112). The other grab rows stay (pinch → rotate by circling). The assemble row reads the joining hand's target, the first row of this spec to do so for a pinch; the rotate rows still ignore it.
116. **Tests and checks.** Unit tests cover the new rows and the unchanged ones (hold + pinch still explode; a pinch on the same object, on the same assembly and on empty space still rotates by circling), the switch (the part restored, nothing committed, no jump), the two-pinch snap committing a join on release, the knob angle from synthetic landmarks (sign, wrap, dead zone, mirrored view) and the freeze of the knob fist. E2E covers two pinches joining the two demo objects (one 復原 undoes the join), a fist knob turning a held part, and a second pinch on the same object still rotating by circling. The synthetic hand has a `roll` option, in degrees, that turns the hand in the image plane, so tests can twist a fist. Existing tests change only where they list the join rule's rows or assert that a fist is inert while a part is grabbed; `tasks.md` Task 11 lists which. The manual webcam list gets items for both gestures: whether the knob turns the right way, and whether small wrist movements turn it by accident.

### Second-hand pinch must not turn into a fist (Task 12)

Found in the user's webcam test after Task 11: sometimes, while the first hand grabs a part and the second hand pinches, the gesture became the fist-knob rotate instead of the two-pinch join or the rotate by circling. Cause found by reading the code: requirement 90 lets a fist replace a pinch that has not left its dead zone, and a pinch of the second hand that stays still while its curl ratio is below `FIST_ENGAGE_RATIO` for `FIST_ENGAGE_MS` (for example an index finger bent toward the thumb, with the other fingers curled) engaged a fist. The fist made the pinch leave (the rotate by circling ended, an assemble was cancelled) and, with a part grabbed, joined as the knob of requirement 112. The curl ratio of a real tight pinch has not been measured on the webcam yet; the synthetic pinch with the other fingers curled measures about 1.36, so the dip below 1 comes from a bent index finger (the debug line of requirement 45 shows both hands' curl ratio, 曲度, to read it).

117. **A pinch that takes part in a two-hand gesture stays a pinch.**
    - **(a)** A hand whose pinch is part of a two-hand gesture keeps that input until the pinch is released: while the gesture runs (the join, the rotate by circling, the zoom, the explode and the assemble of requirements 82–98 and 108–111), the curl ratio of that hand does not engage a fist and does not hide its pinch distance from the pinch state machine, so the pinch ends the normal way: release (requirement 104), loss (requirement 37) or a gate change (requirement 40). This holds for the joining pinch and for the owner's pinch once a joiner has come, and for a pinch that was made while another hand's gesture runs and that nothing joins (an inert pinch).
    - **(b)** The fist-knob rotate of requirement 112 starts only when the second hand's fist engages while that hand has no engaged pinch: a fist made directly, not a pinch that closed. A pinch that later curls stays a pinch.
    - **(c)** The one-hand rule of requirement 90 stays for a hand that is not part of a two-hand gesture: a single hand's pinch that has not left its dead zone can still close into a fist. The freeze of requirement 101 is unchanged.
    - **(d)** `?hands=debug` shows the curl ratio of both hands (曲度 first／second, requirement 45), so the next webcam test can read the second hand's value while it pinches.
    - **Known limit.** If the curl ratio of the second hand is already below `FIST_ENGAGE_RATIO` while its fingers are still closing, the pinch never engages (requirement 90: a fist-like frame does not count toward a pinch), so that hand is a fist made directly and still gives the knob. The controller cannot tell it from a fist; the measured curl ratio decides whether `FIST_ENGAGE_RATIO` needs to change.
    - **Tests.** Unit tests: the reproduction (a second pinch with a bent index finger, unmoved for longer than `FIST_ENGAGE_MS`, joins as a rotate by circling on the same object and as an assemble on another object, and stays one); the same for the zoom and the explode; the owner's pinch; an inert pinch; release with a curl ratio below 1; a fist made directly still knobs; a single hand's pinch still closes into a fist. An e2e case drives the second pinch with curled fingers on the same object (circle rotate, not the knob). `tasks.md` Task 12 lists which existing test changed and why.

## Decisions to confirm

Small choices made while writing this version; each is easy to change.

1. A fist move reuses the 物件 panel's notice 已調整物件位置，可按「復原」回到上一步。 instead of a new text (requirement 92).
